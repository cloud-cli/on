# on v3: Addressable automation in live channels

**Status:** Living design proposal, updated as the product and syntax discussions evolve. Current decisions replace superseded proposals in place; Git history preserves earlier iterations.

The product is an AI-first, general-purpose automation platform where human messages, workload progress, external events, and agent actions share a channel. Connectors produce typed events, workflows react to events, recipes provide reusable functions, and agents translate intent into event-backed requests. Every execution has a traceable history, and each step can retain the context needed for inspection and replay.

The channel should answer three questions:

1. What is happening?
2. What caused it?
3. What happens next?

All YAML, resource paths, and interfaces below are illustrative design notation. They are not the current workflow schema or an implementation commitment to a particular syntax. Compact schemas such as `room: string` abbreviate typed contracts; their final representation can use JSON Schema. Implementation bodies are omitted where a sample focuses on composition.

## 1. Product direction and boundaries

### General-purpose automation

CI/CD is one application of the platform, not its defining domain. Turning lights on when someone arrives home, reacting to a sensor, scheduling a task, handling a message, and building a repository use the same core primitives. Repository, commit, image, and deployment fields are optional domain data rather than mandatory execution concepts.

The original pain is fragmented automation: repository-local CI files and growing include trees make behavior difficult to discover, reason about, and reuse. The proposed answer is a discoverable library of versioned recipe functions, composed into event-driven workflows and observed in shared channels.

### Automation and external data

`on` owns orchestration, execution metadata, conversation history, event delivery state, and references to the exact versions used by an execution.

Versioned application data lives outside the platform, including at `https://git.api.apphor.de`. Workflows consume and produce that data through external services. The channel can render a referenced version or diff while retaining its external identity and provenance.

Execution sandboxes, logs, and checkpoints support automation. Durable checkpoint contents and larger artifacts can use external storage; `on` records their identities, integrity information, availability, and retention state. This boundary does not introduce a general-purpose repository, document, or application-data hosting product inside `on`.

The earlier webhook-per-workflow and separate-dispatcher proposals are refined here:

- A **connector** understands a source and produces normalized events. A webhook connector has an addressable webhook input; other connectors can poll, watch, or schedule.
- A **workflow** reacts to normalized events and has a stable callable identity with an input contract. Calls become addressed request events.
- A **recipe** groups reusable, named functions that implement work.
- An **agent** interprets messages and events and can request permitted workflows as tools.

Connector and dispatcher are merged into one authored primitive, **connector**. Dispatching remains runtime routing behavior. Event publication is durable before consumer execution, so producers and consumers have independent lifecycles.

### Channel-first interaction

The primary workspace for doing work is a channel. People should be able to observe a run, inspect its logs and inputs, discuss a failure, follow an agent investigation, and start a related execution without leaving the conversation.

The design references combine Slack-style conversation, GitHub Actions-style execution detail, and inline views of externally versioned Git data. Native channels in `on` are the primary interface described here.

## 2. Four authored primitives and their runtime model

### Authored primitives

- **Connector:** a configured, versioned source adapter that authenticates or observes signals, normalizes them, and emits typed events.
- **Recipe:** a versioned module exposing named functions with declared inputs, outputs, runtime needs, and implementation steps. Recipes can be internal or public.
- **Workflow:** a versioned reaction to events, with a canonical input contract, entry conditions, recipe-function composition, and typed outputs. Its callable identity is also available through an addressed request binding.
- **Agent:** an identified participant with instructions, event/message subscriptions, and explicitly assigned workflow tools and automation capabilities.

`kind: connector`, `kind: recipe`, `kind: workflow`, and `kind: agent` distinguish illustrative definitions. **Automations** is the combined UI area, rather than another schema primitive.

### Organizational and runtime concepts

- **Workspace:** the organizational and authorization boundary for members, secrets, integrations, recipe/workflow ownership, runner access, and channels.
- **Channel:** a shared operational purpose, such as `#release-ops`, `#backend`, or `#home-automation`, containing messages and views of relevant events.
- **Invocation:** an addressed request to execute a workflow, including its acceptance or filtering outcome and pinned revision.
- **Run:** the execution of an accepted invocation, including any declared matrix variants.
- **Function call:** an invocation of a recipe function within an execution, with its own call-site identity and nested steps.
- **Step attempt:** one immutable execution record with its input context, checkpoints, outputs, logs, and outcome.
- **Event:** an immutable record with a unique identity, a named type, a schema version, and causal context. Domain facts, addressed requests, and execution outcomes retain their different meanings.
- **Subscription:** a durable runtime binding compiled from a workflow's `on:` declarations or an agent's configuration. It is not a mandatory fifth authored primitive.
- **Sandbox:** the execution directory and declared runtime filesystem boundary of a run. This term avoids confusing an execution directory with an organizational workspace.

A channel can relate to several connectors, workflows, agents, and external resources. A workflow can consume inputs from several sources. The same execution can appear in multiple channels without being duplicated.

Existing workspaces can begin with a default `#activity` channel and add purpose-specific channels later.

## 3. Architecture overview

```text
Presence / Sensors / Webhooks / Timers / Channel messages
                            |
                            v
                 Connectors and built-in producers
                   authenticate -> normalize -> emit
                            |
                            v
                       Durable events <----- Addressed tool requests
                            |                           ^
                +-----------+------------+              |
                |                        |              |
                v                        v              |
       Workflow on: reactions    Agent subscriptions ----+
                |
                v
       Workflow invocation admission
  authorize -> pin revisions -> validate -> filter
                |
                v
       Queue and execution workers
       versioned recipe functions
       checkpointed step attempts
                |
                v
       Typed results and runtime completion events
                |
                +----> Further workflow/agent reactions
                +----> Channel cards and conversation

Execution data references external Git / artifact / domain services.
```

An event can be accepted while its consumers or execution workers are unavailable. Each registered consumer has its own delivery state and catches up independently. Accepting an event, accepting a workflow invocation, queueing work, and finishing execution are separately observable states.

Function-shaped calls from people, agents, or other automation are bridges into addressed request events. They share the event-backed admission and execution path; they do not run a workflow inline inside the caller. Internal bridges need no loopback HTTP request.

## 4. Connectors own event production

### One source-adaptation primitive

The original runner was generic. Provider preprocessors adapted Git events, but integrating their routing and payload conventions into workflows mixed external integration with reusable automation.

A connector owns source adaptation and event production. The previously proposed dispatcher has the same responsibility and is folded into this primitive. Runtime dispatch selects consumers after event persistence.

Provider-specific signatures, delivery identifiers, headers, payload shapes, and lookup behavior belong to the connector implementation. Workflows consume normalized contracts and can remain unaware of the originating provider.

### Connector syntax and output events

```yaml
kind: connector
id: home_presence

using: presence/geofence@v1

with:
  zone: home

emits:
  entered: presence.arrived
  exited: presence.departed
```

`using` selects a reusable connector implementation and version. `with` configures the instance. `emits` maps declared output ports to workspace event types with compatible payload schemas; renaming an event must not silently change its data contract.

For example, `entered` can produce:

```yaml
eventId: evt_presence_123
type: presence.arrived
schemaVersion: 1
workspaceId: home
source: connector/home_presence
data:
  person: alex
  location: home
```

Webhook connectors expose webhook addresses. Polling connectors have polling lifecycles. Timer connectors have schedules. Channel messages and agent mentions use built-in producers with the same event envelope. Their shared behavior is durable typed-event production.

### Connector lifecycle

```text
Receive or observe a signal
  -> record source identity and receipt time
  -> authenticate / verify the source where applicable
  -> deduplicate the source occurrence
  -> resolve and pin connector implementation/configuration revisions
  -> normalize data and validate the output contract
  -> apply source relevance conditions
  -> persist emitted events and publication state
  -> let registered consumers react independently
```

Source verification uses the original request representation where required. Filtered, rejected, duplicate, and unmatched deliveries have distinct observable outcomes. An unverified delivery can have an ingress diagnostic record without becoming a trusted domain event.

Connector instances are workspace-owned and configurable for particular sources, devices, organizations, or integrations. Their behavior and mapping revisions must be recorded so an investigation can explain exactly how a signal was interpreted. Whether any workflow matched an emitted event is a separate consumer-side outcome.

Connectors may reuse recipe functions or execution primitives for complicated transformations. Their product contract remains event production; source-specific behavior does not become implicit behavior of every generic workflow.

### Git as one connector family

A GitHub connector can be attached to an organization or repository through its webhook address. GitLab, Gitea, Forgejo, and the local Git service can produce the same versioned Git event contract. That allows a single build workflow to react to changes from any of those sources.

A normalized Git input should identify at least:

- The logical repository identity.
- The clone location selected for this execution.
- The immutable commit to build.
- The ref and operation represented by the event, where applicable.
- The repository owner and name as useful labels.
- Source provenance and delivery identity in the event or invocation envelope.

Credentials are supplied through scoped secret references, rather than being embedded in clone URLs or event payloads.

An illustrative normalized event is:

```yaml
eventId: evt_01_example
type: git.push
schemaVersion: 1
workspaceId: acme
source: connector/github-acme
subject: repository/github/org/example
correlationId: corr_01_example
causationId: ingress_01_example
data:
  repositoryId: github/org/example
  cloneUrl: https://git.api.apphor.de/git/org/example.git
  owner: org
  repo: example
  ref: refs/heads/main
  commit: <immutable-commit-sha>
```

The logical repository identity and the physical clone location are separate. A GitHub-originated event can build from a local mirror on `git.api.apphor.de` while preserving GitHub provenance and the exact source commit.

Mirror routing must verify that the selected mirror has the requested commit. A delayed mirror is an explicit readiness condition; it must not silently substitute its current branch head. Copies of the same change arriving from the origin and mirror need a configurable semantic deduplication rule if they represent one intended build. Legitimate distinct events must remain distinguishable.

## 5. Recipes are modules of callable functions

### Stable modules, functions, and call sites

A recipe groups related reusable functions, such as:

```text
docker/login(credentials) -> registrySession
docker/build(source, options) -> image
docker/push(image, registrySession) -> publishedImage
docker/publish(source, options, credentials) -> publishedImage

lights/turn_on(room) -> state
lights/turn_off(room) -> state
```

The higher-level `docker/publish` function can compose login, build, and push. Named script steps gain discoverable signatures, namespacing, versioning, and composition rather than being copied across repository-local files or include trees.

Each recipe has a stable identity. Each callable function has a stable ID within the recipe, and each implementation step has a stable ID within its function. Authors choose the exported functions; internal helper steps remain inspectable without automatically becoming public API.

A versioned function reference can be `platform/docker@v3/build` or `home/lights@v1/turn_on`. Version the recipe module as a coherent unit. Local aliases make calls familiar, while the execution record stores the fully resolved module version, function, call site, and transitive dependencies.

Calling the same function twice creates two call instances with distinct execution paths. A function's definition ID identifies reusable code; its call-site and attempt IDs identify particular work.

### Recipe syntax

```yaml
kind: recipe
id: home/lights
version: 1

functions:
  turn_on:
    inputs:
      room: string
    outputs:
      state: string
    steps:
      - id: send_command
        # Implementation goes here.
```

A workflow or another recipe function can compose exported functions:

```yaml
recipes:
  docker: platform/docker@v3

steps:
  - id: build
    call: docker/build
    with:
      source: ${inputs.source}

  - id: publish
    call: docker/push
    with:
      image: ${steps.build.outputs.image}
      registrySession: ${inputs.registrySession}
```

This is a composition fragment; its enclosing definition supplies the input and output contracts. Public and private workspace recipes use the same calling model and retain their access rules. Published versions are immutable, and existing runs retain their original function definitions.

### Explicit state and nested execution

Functions declare inputs, outputs, runtime requirements, effects, and any shared sandbox dependencies. A function must not silently depend on a previous unexposed step changing the working directory, credentials, or host state. A registry session can be a scoped capability reference rather than raw credentials in outputs.

Recipe functions are executable operations and can have side effects. Function syntax does not imply mathematical purity; the checkpoint and effect-retry contracts still apply.

The channel shows a high-level call such as `docker/publish` and expands it into its nested calls and steps. Each nested attempt retains its own inputs, logs, outcome, and checkpoint references. A compact interface and complete execution history use the same underlying call tree.

## 6. Workflows react to events and expose callable contracts

### Stable identity and reusable behavior

A workflow has a stable, unique identity. Calls use that identity, rather than a mutable display name. A workspace remains the authorization scope, even if workflow IDs are globally unique. Short symbolic references resolve in an explicit workspace context.

```yaml
kind: workflow
id: lights_on

inputs:
  room: string

on:
  - event: presence.arrived
    if: event.data.person === 'alex'
    with:
      room: hallway

recipes:
  lights: home/lights@v1

steps:
  - id: switch
    call: lights/turn_on
    with:
      room: ${inputs.room}
```

`on:` declares normalized event reactions and maps event data into canonical inputs. `inputs` and `steps` describe the reusable operation. The example abbreviates the output contract and result binding; the final schema must make both explicit.

Provider payload interpretation remains in the connector. A presence event from any compatible source can start this workflow. The same operation can also be requested by ID with `{ room: 'office' }`.

An organization can express much of its automation through a small number of generic workflows such as build, verify, and release. Repository, commit, environment, and configuration are inputs. A new data source does not require another copy of the workflow.

The same principle applies to home automation, notifications, data processing, and agent tasks. Recipe functions provide the reusable implementation, while workflows provide reactions and composition. Workspace-specific bindings and secrets remain explicit. Cross-workspace calls require an explicit grant; knowing an identifier alone does not grant execution access.

### Declarative reactions and explicit requests

`on: presence.arrived` declares a standing reaction. `lights_on({ room: 'office' })` expresses a particular request. The useful distinction is **subscription versus invocation**, rather than whether the surface happens to be YAML or function-shaped syntax.

A YAML call can be a declarative description of an invocation, and function-shaped syntax can describe a dependency graph. Both surfaces use the same recorded execution model.

The runtime compiles `on:` declarations into versioned durable subscriptions. Authors do not need a separate subscription file or dispatcher definition for an ordinary reaction. Subscription identity, delivery state, and revision remain inspectable runtime concepts.

Every callable workflow also has a system-provided binding for addressed workflow requests. Its authored `on:` entries add reactions to domain events; they do not need to describe agent tool transport or API internals.

### Invocation contract

Connectors publish domain events. API and tool bridges publish addressed request events. Workflow invocation admission consumes the appropriate durable event and follows the same rules:

1. Resolve the caller, target workflow, and workspace authorization.
2. Identify the source event, reaction or addressed request, and its deduplication identity.
3. Resolve and pin an immutable workflow revision and recipe versions.
4. Map reaction data where applicable and validate canonical inputs.
5. Evaluate the workflow's provider-neutral entry condition.
6. Record acceptance, filtering, or rejection and its reason.
7. Queue accepted work with the captured input context and causal links.

A stable HTTP invocation resource can expose this contract to external callers by recording an addressed request. Source webhook endpoints belong to connectors. Request and event acceptance are observable separately from invocation acceptance, execution, and completion.

The request bridge returns a durable request/invocation handle. The caller can follow or await the correlated result without executing the workflow in its own process. Completion, cancellation, and failure propagation remain explicit rather than following an accidental synchronous call stack.

### Filtering stages

Filters have distinct responsibilities:

- **Connector condition:** is this source signal relevant, and which normalized events should it produce?
- **Reaction condition:** should this workflow react to this particular normalized event?
- **Workflow entry condition:** should this valid set of canonical inputs execute?
- **Step condition:** should this step execute in the captured execution context?
- **Output contract validation:** did the run produce the result it promised?
- **Downstream reaction condition:** should a completed result cause further work? An optional future custom-emission condition can govern additional domain events.

Reaction conditions select events. Workflow entry conditions apply to every invocation, including agent and API requests. An entry rejection prevents execution and remains visible in the timeline. An output contract violation is a failed contract outcome. Suppressing downstream work cannot undo already performed work or hide its completion record.

Filters that depend on changing external information must record that information or its immutable reference. Re-reading a mutable source while claiming to reproduce a historical decision is not exact replay.

### Typed results and completion-driven composition

Workflow outputs are explicit, validated, versioned contracts. Examples:

```text
lights_on
  inputs: room
  outputs: room, state

build_and_publish
  inputs: cloneUrl, commit
  outputs: imageDigest, sourceCommit, testReportRef

release
  inputs: imageDigest, environment
  outputs: deploymentId, deployedDigest, healthReportRef
```

The initial model gives workflows typed outputs and has the runtime publish `workflow.completed` with the execution identity, workflow revision, status, relevant input context, and validated outputs or their immutable references. Another workflow can react:

```yaml
on:
  - event: workflow.completed
    if: event.data.workflowId === 'lights_on' && event.data.status === 'success'
    with:
      room: ${event.data.inputs.room}
```

The downstream workflow declares its own canonical input/output contract and steps. Invalid outputs produce an explicit failed contract outcome; a process exiting successfully alone does not establish successful contract completion.

Earlier sketches used `post.dispatch` or function-style calls to another workflow. If offered as authoring sugar, these produce addressed request events through the same durable path. Recipe-function calls remain nested implementation work; requesting another workflow creates a separately tracked invocation.

Each follow-up records its source run/event, reaction or action identity, selected target revision, mapped inputs, and resulting invocation. Repeated delivery of the same logical action returns the same downstream invocation. Parent execution status, follow-up delivery status, and child execution status are separately visible.

A parent can finish its own work successfully while a child later fails. An explicitly awaited child would be a different declared relationship. Delivery failures are retried from recorded outputs without repeating the parent computation or its external effects.

Custom workflow domain events such as `artifact.ready` remain an optional extension to specify. Connector outputs and runtime completion events are sufficient for the initial event-first model.

## 7. Uniquely addressable events

### Event type, event occurrence, and subscription

The proposed named-trigger idea fits well when three identities are explicit:

- **Event type:** `presence.arrived`, `git.push`, or `workflow.requested`, with a versioned payload schema. This is the address used to publish a kind of record or subscribe to it.
- **Event occurrence:** one immutable event with a unique `eventId`. This is the identity used for inspection, replay, causal links, and deduplication.
- **Subscription:** one independently identified routing rule consuming a type of event and producing work.

`git.push` names a stream of occurrences, not one uniquely identified occurrence. Its effective namespace includes the workspace and schema version. Type names alone do not confer publication rights or cross-workspace visibility.

### Production and reactions have separate syntax

Connectors declare their normalized output ports with `emits:`. Workflows declare reactions with `on:`. The runtime persists resulting events and compiles reactions into subscriptions.

An earlier sketch proposed:

```yaml
trigger:
  - name: git.push
    with:
      cloneUrl: https://git.api.apphor.de/git/foo/bar.git
      org: foo
      repo: bar
      commit: <immutable-commit-sha>
```

That form would mean publishing a typed event with supplied data, rather than subscribing or directly executing a target. If general publishing syntax is introduced, `emit` or `publish` is a clearer name than overloading `trigger`. The final schema should also settle whether the Git owner field is named `org` or `owner` and validate it consistently.

Addressed requests express intentional coupling to one workflow. Published domain facts support zero, one, or several consumers. One completion event can cause notification, verification, and agent observation without the producer managing each consumer's execution.

### Facts and commands

`presence.arrived` or `git.push` should represent an actual observed or explicitly simulated occurrence. A request to perform work is represented by an addressed `workflow.requested` event or another clearly defined request type. A tool call must not fabricate a source fact merely to start work.

Transport receipt, normalized domain facts, workflow lifecycle events, human messages, and agent actions can share an event envelope while retaining their distinct types and provenance.

Completion facts remain observable regardless of downstream reaction filters. If custom workflow emissions are added, suppressing one of them must still leave the completion record available to channels and observers.

### Delivery and replay

Record at least:

- Event ID, workspace, type, and schema version.
- Source and actor identity.
- Subject, correlation ID, and immediate cause.
- Occurrence time, receipt time, and durable stream sequence.
- Structured payload or immutable external payload references.
- Related invocation, run, step-attempt, and external data references.

Each subscription delivery records its subscription revision, event identity, mapping result, filter decision, and target invocation. Changes to routing affect future decisions; historical decisions remain explainable.

Each consumer has its own cursor or delivery state; an event is not globally consumed by the first workflow to handle it. Registered consumers recover missed work after downtime. New reactions begin at a defined registration boundary unless historical delivery is explicitly requested, so adding an automation does not unexpectedly execute the entire retained history.

Delivery is at least once, with idempotent consumers. A logical delivery key can combine event ID, subscription revision, and action identity. Retries preserve that key. A deliberate new execution is represented as a new request with explicit lineage.

Replaying an event for inspection or rebuilding a channel projection must not implicitly reissue workflow commands. Deliberate redelivery and re-evaluation against new routing are separate operations and are visible as such.

Causal ancestry, bounded dispatch policies, and agent reaction rules prevent accidental feedback loops while allowing intentionally declared recurring automation.

## 8. Frozen step attempts and replay

### The unit of history is a step attempt

Every step attempt has an immutable record. A retry, replay, or modified execution creates a new record linked to its predecessor.

```text
Before
  workflow revision and step definition
  resolved recipe versions, function IDs, and nested call path
  resolved inputs and prior outputs
  source/data commit references
  runtime/image identity and dependency references
  environment and secret-version references
  starting sandbox checkpoint

Execution
  logs, timestamps, exit status, and observed external actions

After
  validated outputs
  resulting sandbox checkpoint
  output/event identities and delivery state
```

Workflow and recipe revisions, resolved inputs, evaluated conditions, runtime identities, and routing choices are pinned when relevant decisions are made. Mutable names such as a branch or image tag can be retained as labels, but the execution record identifies the actual commit or digest used. Updating a recipe alias cannot change the implementation of a historical nested call.

### Preserve failure evidence

A failed workflow does not wipe its sandbox as a consequence of failure. Preserve:

- The starting checkpoint of its failed step, for replay.
- The failed-state checkpoint, including partial work, for investigation.
- The immutable input/output and log records of earlier steps.

Retaining only the final directory cannot reconstruct the starting state of an arbitrary earlier step. Replays materialize a separate sandbox so inspection and re-execution do not mutate the original evidence.

Local retained state is useful immediately. Durable replay on another worker also requires external checkpoint contents or complete reconstructible references. Retention is explicit and visible; checkpoint expiry or unavailable external data changes the reported replay availability rather than silently selecting newer data.

### Filesystem and external-state boundaries

Checkpoint the declared sandbox boundary, with a manifest identifying captured files, metadata needed for restoration, and external references. Caches can be declared regenerable. Injected credentials are excluded from snapshots and restored through authorized secret-version references.

Versioned input/output documents and manifests can live on `git.api.apphor.de`. Larger filesystem snapshots and binary artifacts can use external artifact storage. The current Git service supports immutable-ref reads and atomic commits; those features support reference-based provenance without assuming that every build directory should become application data in Git.

A checkpoint captures declared filesystem and execution context. It does not automatically capture running process memory, arbitrary host state, a remote service, or the external world.

When external checkpoint persistence is incomplete, the attempt must expose that state. Uploading a checkpoint can be retried without rerunning the command. A completed effect must not be repeated merely because its checkpoint upload failed.

### Predictable inputs and external effects

Exact replay requires all relevant inputs to be captured or immutable. A JSON payload and source commit are insufficient when a command also reads the clock, a changing API response, a mutable dependency, or an undeclared host path.

External reads can be modeled as steps whose recorded outputs are reused by downstream steps. Runtime and dependency versions belong to the replay context. If a required secret version or snapshot is unavailable, report the limitation explicitly.

Effectful actions have a separate repeatability contract. Recomputing a transformation differs from publishing a package or repeating a deployment. Where supported, external actions use stable operation identities across retries, with recorded results and reconciliation after an uncertain response.

Replay capability is declared and verified where the execution driver can enforce it. The UI distinguishes reproducible computation, effect-safe retry, and inspection-only attempts. Arbitrary shell execution does not become deterministic solely because its input object is frozen.

### User-facing execution actions

- **Inspect checkpoint:** view the captured input or failed state without running anything.
- **Replay this step:** create another attempt using the original definition, inputs, and starting checkpoint, according to its effect contract.
- **Resume from here:** create a derived execution branch, reuse the captured completed prefix, and execute the remaining steps.
- **Run with changes:** create a new invocation with explicit input, definition, runtime, or source changes.
- **Redeliver outputs:** retry recorded follow-up delivery without repeating computation.

Reused prefix steps remain references to their original attempts. A changed output invalidates dependent results; they must be recomputed unless their full recorded dependencies still match an explicit reuse policy.

An inspection or diagnostic replay does not automatically publish another set of business events. A resumed or deliberately forked execution declares how propagation continues. Retries of the same logical effect retain its identity; genuinely new work receives a new identity with lineage.

## 9. Live channels and interface design

### Information architecture

The primary layout consists of:

- A workspace switcher and channel sidebar.
- A channel header with its purpose, participants, search, and run action.
- A compact **Now** strip for active work and important current state.
- A mixed chronological timeline.
- A persistent composer for messages, agent mentions, and commands.

Workspace navigation has three primary working areas:

- **Channels:** observe execution and discuss work with people and agents.
- **Automations:** configure connectors, normalized-event reactions, and workflows together.
- **Recipes:** discover, author, and maintain reusable internal or public function modules.

Settings and agent configuration remain accessible in their workspace/channel context. A separate page for every backend entity is unnecessary. "Automations" covers event reactions, schedules, direct requests, and agent tasks; "Integrations" can label external connection settings within that page. The schema can retain `kind: workflow` while the UI presents workflows as automations.

### A combined Automations page

Show connections and behavior in one relationship-oriented view:

```text
Home presence                            Connected
  -> presence.arrived
     -> Turn on arrival lights            Enabled
        Uses home/lights@v1/turn_on

GitHub · cloud-cli                       Connected
  -> git.push · main
     -> Build and publish                 Enabled
        Uses platform/docker@v3
        -> workflow.completed · success
           -> Deploy staging              Enabled
```

The user can inspect a connector, edit an `on:` mapping, open a workflow, inspect its recipe functions, and follow its latest run from the same page. The view exposes relationships without requiring a visual graph editor or collapsing all configuration into one enormous file. Connector health, automation enablement, and run status retain their separate meanings.

Operational inspection remains accessible inline from channel events.

```text
Workspace          # release-ops                 Search   New run
----------------------------------------------------------------
Channels           Now: 2 running · 1 needs attention
# release-ops      Production: v1.24.0 · a3f9c2d
# backend          ---------------------------------------------
# agents
                   Sarah
                   Let's release the billing fix.

                   GitHub delivery received
                   -> git.push · main · a3f9c2d

                   + Build and publish #1247 ------- Running --+
                   | Checkout ✓   Build ✓   Publish ◉           |
                   | Publishing image · 2m 14s                  |
                   | Details v                       3 replies |
                   +-------------------------------------------+

                   Release agent · Observing
                   Tests passed. Watching artifact publication.

                   ---------------------------------------------
                   Message, @mention an agent, or /run...
```

The visual direction combines the breathing room of the first supplied design with the compact event hierarchy of the second. Use restrained surfaces and reserve saturated color for status and interaction. Human messages, machine events, live cards, and agents should be recognizable without making every row visually compete for attention. This release-oriented mockup is one use case; home and other automations use the same components with domain-appropriate fields.

### History and current state

**Events preserve history. Cards show current state.**

A receipt or completion event records what happened at a point in time. A run card is a live projection of one execution. Step transitions update that card in place. Significant milestones can add compact entries at the current point in the timeline linking back to it.

The Now strip keeps active runs visible after their original cards scroll away. It handles concurrent runs rather than assuming a channel has one active pipeline. Environment state, such as the currently deployed digest, is separate from the latest run's outcome.

Headers, cards, and step lists derive their status from the same authoritative run state. An agent's interpretation does not become the source of execution status.

### Compact and expanded cards

A compact run card shows:

- Workflow name, stable run identity, and attempt or derived-execution relationship.
- Status and active step.
- Branch and exact commit, when applicable.
- Completed step count and elapsed time.
- Relevant actions, replies, and downstream work.

Prefer "3 of 5 steps complete" over a progress percentage that assumes equal step duration.

Expanded details include:

- **Summary:** outcome, useful explanation, and important outputs.
- **Inputs:** canonical data, source delivery, immutable references, and revision.
- **Steps and logs:** selectable attempts, bounded live output, and timing.
- **Outputs:** validated results and emitted event references.
- **Changes:** inline source or externally versioned data diffs.
- **Artifacts:** previews and downloads from their storage location.
- **Checkpoints:** starting and resulting sandbox references and replay availability.
- **History and downstream:** prior attempts, decisions, deliveries, and related runs.

Details can be grouped to avoid an excessive tab bar, especially on smaller screens. Inspecting a commit or generated file follows its external version reference. A permalink opens the channel at the exact event or card, expands the requested detail, and preserves causal context.

A recipe function call such as `docker/publish` initially occupies one row. Expanding it reveals login, build, and push with their own call-site/attempt identities, inputs, logs, and checkpoints. The default view stays compact while allowing complete inspection of nested execution.

### Readability and interaction rules

- Human messages receive normal conversational space.
- Routine machine events use quiet, single-line entries.
- Runs and investigations use structured cards.
- Agents have named identities and a clear badge.
- Failures and requests for input receive stronger emphasis.
- Related ingress, normalized events, runs, and follow-up calls are grouped by cause.
- Log lines stay inside their run or step detail.
- Detailed investigation lives in replies, with its outcome surfaced in the main timeline.
- Card updates preserve scroll position and do not repeatedly mark every log chunk unread.
- Readers of older messages see a new-activity indicator instead of forced scrolling.
- Filters affect the visible projection, not agent subscriptions or the underlying event history.
- Search can find messages, runs, commits, events, and agent actions within authorized scope.

On mobile, details expand vertically and a step selector appears above logs. Keyboard navigation, focus management, readable contrast, and textual status labels are part of the interaction design.

### An execution graph inside a conversation

```text
Webhook received by GitHub connector
  -> git.push emitted
     -> Build #81
        -> Checkout succeeded
        -> Build succeeded
        -> Verify failed
           -> Human reply and agent investigation
           -> Replay of Verify succeeded
           -> Resumed execution succeeded
              -> workflow.completed · success
                 -> Release #29
```

The default view is compact and conversational. Expansion reveals the graph. A successful build and failed deployment retain their individual outcomes while the channel can summarize the overall operation.

The same layout can show `presence.arrived -> lights_on -> home/lights/turn_on -> completion`, or a channel mention followed by an agent's correlated request and result. Device state and other domain outcomes are as natural to the channel as deployment state.

## 10. Agents as first-class participants

### Visible responsibility and activity

Each agent has a name, role, configured capabilities, and visible activity state such as Observing, Investigating, Acting, or Paused.

For example:

> Release agent: watches deployment failures, checks health results, and retries a declared transient failure once.

Agents observe structured events and human messages through durable subscriptions. Cheap event matching and batching decide when a model turn is needed. Continuous observation does not require repeatedly sending the complete channel history to a model.

### Agent syntax and workflow tools

```yaml
kind: agent
id: housekeeper

instructions: Help manage the home.

tools:
  - workflow: lights_on
```

The tool catalog derives each permitted workflow's argument schema and descriptions from its canonical input contract. Tool availability is explicitly assigned; discovering a workflow ID does not automatically authorize its execution.

When someone writes `@housekeeper turn on the office lights`, the channel produces an addressed mention event. The agent can choose the typed tool call `lights_on({ room: 'office' })`. The bridge records:

```yaml
eventId: evt_request_456
type: workflow.requested
schemaVersion: 1
workspaceId: home
source: agent/housekeeper
target: lights_on
requestId: req_456
correlationId: conversation_123
causationId: evt_mention_123
data:
  room: office
```

This request follows the durable event-backed invocation path. The target input schema, authorization, workflow entry conditions, revision pinning, and deduplication rules apply just as they do to other requests. Its authored presence reaction does not need to pretend that someone arrived home in order to accept an explicit office-light request.

The agent receives a durable handle, then a correlated completion or rejection result. It can await the result or report that work is queued while the live card shows progress. Completion, timeout, and cancellation need explicit tool-result semantics; receipt of a request must never be reported as completed work.

The message, mention, model response, tool request, invocation, function calls, and result remain linked in the same conversation. Agents can both request particular work and, when granted configuration capabilities, establish standing declarative reactions for future events.

### Context assembly

An agent's context combines:

- Recent relevant events and conversation.
- Authoritative run, step, and environment state.
- Pinned channel goals and recorded decisions.
- A bounded summary of older relevant context.
- Logs, checkpoints, files, and diffs retrieved by immutable reference when needed.

External content retains its source and role in that context. Authorization follows workspace and resource access. UI filters do not silently change the agent's view of its subscribed stream.

### Actions and evidence

Workflow contracts provide discoverable, structured tools for agents. Agents invoke the same workflow IDs, schemas, entry conditions, and replay operations available to other callers.

An agent contribution should make its operational intent, evidence, action, and result understandable:

> Investigating #1247: image download timed out.
>
> Action: requested one retry under the channel's retry rule.
>
> Result: retry succeeded; deployment health check passed.

These entries link to the source failure, relevant evidence, and resulting execution. They report useful explanations and observable actions rather than an unbounded internal reasoning transcript.

Autonomy is defined through concrete capabilities: workflows an agent may start, failures it may retry, external resources it may update, and reaction budgets. Pausing an agent is a direct channel action.

Agents have persistent consumption cursors, idempotent actions, causal ancestry, and bounded reaction rules. These allow recovery after interruption and avoid repeated reactions to their own output.

Model responses are nondeterministic results with their own attempt records. Downstream replay can reuse a recorded response. Asking the model again creates a new attempt; it is not represented as reproduction of the original response.

## 11. Durable history and state projections

The existing live notification transport is a useful starting point. Durable channel history and autonomous observers need persisted records, stable cursors, and reconnection behavior in addition to live delivery.

### Persistence model

Persist execution transitions, their metadata, and an event/outbox record atomically where they share the orchestration database. Publish only committed records. External checkpoint contents are persisted and verified separately; their durable references and availability transitions are then recorded in the orchestration state.

Workers report outcomes under their execution identity. Repeated reports and deliveries converge on the same logical state. A stale worker or delayed event must not overwrite a newer attempt or projection revision.

The durable model needs records for:

- Connector implementations, instances, configuration revisions, and emitted-event identities.
- Ingress receipts and interpretation/routing outcomes.
- Recipe versions, exported functions, and pinned dependency references.
- Workflow revisions, compiled `on:` bindings, request events, and invocation decisions.
- Runs, nested function calls, immutable step attempts, and checkpoint references.
- Typed events, independent consumer cursors/subscriptions, and delivery attempts.
- Channel messages and event visibility/bindings.
- Agent subscriptions, cursors, actions, and resulting executions.

Large or sensitive source data is represented by appropriate external references and filtered diagnostic views. Execution metadata is sufficient to establish provenance without turning channel history into a general data warehouse.

### Ordering and recovery

Use a durable sequence within the chosen stream scope for pagination and reconnection. Preserve occurrence and receipt timestamps separately; timestamps alone cannot establish reliable delivery order. Causal links explain dependencies across streams and concurrent runs.

Browsers and agents resume from their cursors, deduplicate events, and reconcile current state. SSE can remain the delivery transport. Projection rebuilds are read-side operations and do not re-execute automation.

Channel bindings reference canonical events and runs. Showing an event in several channels does not create several events or several workflow invocations. Channel configuration controls visibility; subscriptions control execution.

## 12. Existing foundations and required changes

The current code already provides useful building blocks:

- Workspace/team isolation, memberships, secrets, and runner grants.
- DB-authored workflow revisions and immutable revisions pinned to queued jobs.
- Reusable, versioned recipes.
- Structured step outputs and authenticated downstream dispatch.
- Idempotent dispatch per source job and step, with parent-run linkage.
- Run details, logs, artifacts, controls, and AI-assisted failure diagnosis.
- SSE job-change notifications.

Relevant implementation locations include:

- `src/server.ts`: ingress, workflow matching, and HTTP APIs.
- `src/events.ts`: current live event broker.
- `src/queue.ts`: queue, dispatch deduplication, and restart behavior.
- `src/worker.ts`: step execution, output context, reports, and file capture.
- `src/types.ts` and `workflow.schema.json`: workflow and execution contracts.
- `src/ai-help.ts`: diagnostic context assembly.
- `ui/run.html` and `ui/run.mjs`: run inspection and interaction.
- `ui/app-shell.html` and `ui/app-router.mjs`: workspace navigation and routing.
- `docs/feature-requests.md`: proposed observable ingress and validation context.
- `docs/workflow-syntax.md`: current provider aliases and downstream dispatch.

Important semantic changes are explicit:

- Provider-specific `on:` parsing moves into connectors; normalized-event `on:` reactions remain on workflows and compile into durable subscriptions.
- Connector and dispatcher collapse into one authored primitive; dispatch remains runtime routing behavior.
- Existing recipes containing inputs and a step sequence expand into versioned modules with named function exports and explicit call identities. The migration must define a compatible default entry point for existing recipe versions.
- Workflow input/output contracts and generic entry conditions become first-class, and tool/API calls enter through addressed request events.
- Current restart behavior selects the active revision; exact replay must preserve the original revision and captured context.
- Current successful-run artifact/cache capture is not step-level checkpointing, especially for failed attempts.
- Current SSE notifications are transient and do not provide durable replay history.
- Existing post-step hooks and direct child dispatch do not yet define event-backed request admission or reliable runtime completion-event delivery.
- Current identifiers normalize separators; the final callable naming syntax must preserve existing identities and define how symbolic aliases such as `build_and_publish` resolve.

Adoption should preserve existing workflow/run identities and historical revisions. Legacy provider-triggered definitions can be represented by explicit connector instances and normalized-event `on:` bindings while their generic execution behavior is extracted. Existing recipe references need a stable compatibility entry point. Historical records remain interpretable under the schema and configuration versions that produced them.

### Slice 3: checkpoints, replay, and reliable composition

- Record immutable step attempts and pre/post sandbox checkpoints.
- Preserve failed sandboxes and publish accurate checkpoint availability.
- Implement distinct inspect, replay, resume, changed-run, and redelivery operations.
- Validate output contracts and persist runtime completion events/follow-up requests with idempotent delivery.

## 14. Acceptance criteria

### General-purpose primitives and recipe reuse

- Presence, timer, channel-message, and Git events use the same durable event and execution model without requiring CI-specific fields.
- Connector, recipe, workflow, and agent are the authored primitives; dispatcher is runtime behavior and subscriptions are compiled bindings.
- Internal and public recipes expose stable, versioned function contracts with access rules.
- Two calls to the same function have distinct call-site/attempt identities and independently inspectable nested steps.
- Updating a module or alias does not change a queued or historical execution's resolved functions.
- A workflow can compose functions from several recipes without copying their implementation or hiding required runtime/sandbox dependencies.

### Provider neutrality and addressability

- GitHub, GitLab, Gitea, Forgejo, and local Git integrations can produce a shared canonical contract through their connectors.
- A workflow's `on:` binds normalized events rather than provider payloads, and its stable identity accepts validated addressed requests.
- A build can use the same immutable source from an origin or verified mirror without changing its workflow implementation.
- Tool/API requests and event-driven reactions use the same event-backed invocation rules and workspace authorization.
- Every rejected, filtered, duplicate, accepted, or dispatched ingress outcome has an inspectable reason within its authorized diagnostic view.

### Event composition

- Event types, occurrences, subscriptions, and delivery attempts have distinct identities.
- Events are accepted independently of consumer/worker availability, and registered consumers recover using their own delivery state.
- New reactions do not execute retained historical events without an explicit historical-delivery policy.
- Schema-invalid inputs do not execute; schema-invalid outputs do not emit a successful domain result.
- Emission filtering does not hide the underlying execution outcome.
- Duplicate source deliveries and delivery retries do not create duplicate logical actions.
- Changing a subscription does not rewrite historical routing decisions.
- Reconnecting a client or rebuilding a projection does not trigger work.

### Replay and retained state

- A failure preserves its starting and failed-state sandbox checkpoints according to the declared retention policy.
- Replaying an eligible step uses its original revision and captured inputs in a separate sandbox.
- Original attempts and evidence remain immutable after retries, resumes, and forks.
- A changed result invalidates dependent results unless an explicit dependency-matching reuse rule applies.
- External effects follow their declared retry/idempotency semantics.
- Missing snapshots, credentials, or external versions produce an accurate replay-availability outcome.
- Durable checkpoints can reconstruct an eligible execution on another compatible worker.

### Channels and agents

- Connectors, event reactions, and workflows are discoverable together on the Automations page; reusable recipe functions have a library view.
- A user can follow a run, inspect logs and checkpoints, discuss it, and initiate a related action inside the channel.
- Live cards, the Now strip, and step details agree on authoritative execution state.
- Multiple concurrent runs remain readable, and updates preserve scroll position.
- Permalinks restore the relevant expanded inline detail.
- Agents resume observation after interruption without duplicating actions.
- Agent context includes relevant messages and structured events independently of UI filters.
- Mentioning an agent can produce a typed workflow request, a live run card, and a correlated result in the original conversation.
- Workflow tool schemas reflect their input contracts, and queued requests are distinguished from completed work.
- Agent actions identify their cause, evidence, operation, and result.
- Desktop and mobile flows support keyboard interaction and show no obvious console/runtime or failed-request regressions during browser verification.

## 15. Decisions to finalize before implementation

The current direction is a general-purpose event-driven system with four authored primitives, a combined Automations interface, external data storage, live channels, and immutable execution history. The following details need a concrete specification:

1. The final YAML vocabulary for typed schemas, result bindings, recipe functions, `call:`, connector `using:`/`emits:`, workflow `on:`, and agent tools.
2. Recipe export visibility, function/call-site identity, alias and dependency resolution, module packaging, and compatibility entry points for existing recipes.
3. Workflow request admission, exact-revision addressing, revision-selection timing, and migration of existing IDs.
4. Connector implementation packaging/versioning, output-port contracts, and which transformations run at ingress versus on workers.
5. Event schema-version compatibility, consumer start boundaries, and canonical Git origin/mirror identity and deduplication rules.
6. Whether custom workflow domain-event emission or post-call sugar is needed beyond connector outputs, addressed requests, and runtime completion events.
7. The checkpoint storage adapter, declared filesystem boundary, metadata fidelity, and retention defaults.
8. Effect classification, external-operation reconciliation, and how propagation resumes after replay or a fork.
9. Compiled subscription revision semantics, event retention, stream scope, and deliberate historical redelivery.
10. Channel bindings and default visibility, including events related to several channels.
11. Agent context budgets, action capabilities, reaction/concurrency limits, and asynchronous tool-result/cancellation semantics.

The governing principle is: **every piece of work has a conversational home, a callable contract, a current state, and a traceable execution history.**
